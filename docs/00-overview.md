## 心智模型

```
   原始数据（PDF / 截图 / 照片 / 压缩包 / 录屏 / Excel…）
        │
        │  ← 每个人的数据都不一样，这一段要动脑
        │     build_assets.py（原件 → 资产）+ build_data.py（内容 → 结构）
        ▼
   data.json  +  assets.json          ← 契约：docs/DATA_CONTRACT.md
        │
        │  ← build_html.py，三处字符串替换，纯机械，永远不用改
        ▼
   我的健康档案.html                   ← 模板 template/app_template.html，功能已固化
```

**关键认识**：页面的全部功能——5 个视图、趋势图、报告抽屉、影像灯箱、
批次对比、深浅色、分屏弹窗——都写死在模板里、已充分测试。

**你几乎不碰模板。** 全部工作是把千奇百怪的原始数据规整成契约里那三个 JSON。
数据形态千变万化，但只要产出符合契约，页面表现就完全一致。

这个分工是整个项目的核心：**把「每次都不一样的部分」和「一次做对就不用再动的部分」
彻底分开。**

## 几个设计决定，以及为什么

### 为什么不装 OCR 引擎

上一代工具包用 macOS Vision 做 OCR，那是「没有 agent 在场」时代的方案：
需要一个程序把图变成文字。

**这是个 agent 项目**——跑它的 agent 本身就是多模态模型，`Read` 打开图片就能读。
所以抽取分两层：有文字层的 PDF 用 PyMuPDF 精确取，没有文字层的**交给 agent 看**。

好处不只是少一个依赖：
- **跨平台缺口直接消失**（Vision 只有 macOS 有）
- **读得更准**——OCR 会把 `≥` 认成 `2`、把罗马数字 Ⅲ 认成 11，多模态模型不会
- 依赖只剩 `pymupdf / pillow / numpy / openpyxl`，全是纯 Python

代价是量大时会撑爆上下文，所以留了[可选的第三层](20-extract.md#第-3-层量大到撑爆上下文--可选的子进程分批)——
但**任何 CLI 都不是依赖**，没有就退回第 2 层分批处理。

### 为什么不驱动小程序

医院小程序本质是个魔改的浏览器，**报告本身就是网页**，小程序解决的是「认证」。
所以正确做法是把报告链接搬到电脑 Chrome 里打开，而不是去自动化小程序。
详见 [`11-acquire-mobile.md`](11-acquire-mobile.md)。

### 为什么参考区间要逐次存

因为实验室会改判读标准。同一个数值，在旧标准下正常、新标准下偏低——
只存一个项目级区间必然出错。这不是假想，是真实数据里踩到的
（[坑 §4.3](20-extract.md#43-参考区间会随时间--随报告变-)）。

### 为什么没有「自动核对」

上一代靠 OCR 回读做双源对撞，那一步是整套东西值得信任的原因。
新架构少了第二份数据源，就用**确定性自检**替代：
结构上杜绝（区间逐次存）+ 交叉校验（自算偏离 vs 报告印的箭头）+
有第二份数据时一定对撞。

但**核对结论必须写进 `footNotes`**——用户看到那句话才知道这份档案能信到什么程度。

### 为什么产物是单个 HTML

个人健康数据不该需要服务器、账号、或者信任任何人。一个自包含文件可以：
拷到 U 盘、发给家人、断网打开、十年后还能打开。零外链是硬约束，
`tools/verify.py` 每次都会重新检查。

## 红线

1. **用户数据只留本地** `workspace/`（已 gitignore），永不进 git、永不上传。
2. **不做医学诊断**——只重新组织展示，结论一律摘录原文，页脚免责声明必须保留。
3. **绝不代输账号密码验证码**，只在用户已登录的会话上操作。
4. **产物零外链零 fetch**。
5. **不确定的数字不要编**，标「待核对」告诉用户。
